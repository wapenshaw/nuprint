# Working on NuPrint

## Start here

NuPrint is a **Rust + Tauri 2** desktop app and CLI for Windows, macOS and Linux that prints directly to Bluetooth LE thermal printers. The first supported model is the ZEITEL **lowercase SC03h**; other models are added through protocol drivers and profiles. The original Python app lives in `poc/python` as the verified parity reference.

- Read [README.md](README.md) for supported behavior and commands.
- Read [docs/README.md](docs/README.md) to find product, architecture and printer documentation.
- Follow [docs/rust-tauri-spec.md](docs/rust-tauri-spec.md) and [docs/printer-support.md](docs/printer-support.md). Keep the core independent of Tauri and OS-specific APIs.
- Use [.claude/skills/sc03h-printer/SKILL.md](.claude/skills/sc03h-printer/SKILL.md) for protocol, Bluetooth, printer diagnosis or hardware validation work.
- The full-app documents also describe planned behavior that does not exist yet. They do not authorize implementing the entire roadmap in an unrelated task.

## Verified baseline

On 2026-10-12, the Python PoC connected to `SC03h-3DE8`, queried firmware `3.0.49`, and printed a 384 × 164-dot text/alignment strip; the owner confirmed correct text and border. The same day, the Rust desktop app (Windows dev build) connected to the same unit and sent two short text jobs. The printer reported ready before and after each transfer, and the owner reported the prints working. On 2026-10-13, the Rust app on macOS (Apple silicon) found the same unit after the Bluetooth permission prompt and sent four short text jobs, three from the dev build and one from a packaged debug app, with ready status before and after each; the owner reported them working. Release installers and Linux are unverified. See [docs/validation.md](docs/validation.md).

## SC03h protocol invariants

These apply to SC03h, not every future printer. Other models have independent capability/settings/status definitions; never widen the SC03h matcher as a shortcut to multi-model support.

- `SC03h-` and `SC03H-` are different profiles. Do not broaden model matching or reuse heat values without evidence.
- Settings an owner edits in Printers → Advanced become that printer's own custom profile ([rules](docs/printer-support.md#settings-edited-on-this-computer)). Keep the identity keys (`id`, `protocol`, `match`) locked, keep custom profiles out of discovery, and never rate them above Experimental or copy verification into them. They do not change the SC03h values above.
- This unit advertises **AF30** but exposes print service **AE30**. Name discovery followed by GATT verification is intentional.
- Write to **AE01**; subscribe to **AE02/AE04**. Require a fresh valid A3 status before a print.
- Frames use `51 78`, uint16 little-endian payload length, CRC-8 polynomial `07` over payload only, and `FF` terminator.
- Raw A2 rows are 384 dots / 48 bytes, **LSB-first, 1 = black** on the wire. `MonoBitmap` is MSB-first; the iPrint driver reverses each byte. Keep `tests/python_parity.rs` passing.
- Normal image heat is **5000**, speed parameter **10**, chunk cap **180 bytes**, additionally bounded by negotiated write size. These values live in `profiles/sc03h-iprint-384.json`.
- Extra trailing feed is configurable from 0–12 nominal mm; 12 preserves the verified two 48-step A1 commands, while zero omits post-image feed. BD controls speed, not feed distance. Reduced-feed physical calibration is pending; preserve fresh status/cleanup at zero. Other models need independent feed scales and bounds.
- Queue state is the safety net. A job is claimed durably (`Store::claim_queued`) before any Bluetooth I/O, cancel is a checked transition, and one process owns a data folder (`state.lock`; extra desktop windows use `window-N` folders). Never store typed text or PDF passwords with a job, and wrap any printer name or title in a log line with `private()` so diagnostics can redact it.
- Honour AE pause/resume, maintain pacing and always disconnect on completion, failure or cancellation.
- A successful BLE write is not proof of paper output. Preserve honest completion wording and do not automatically replay partially sent jobs: a failure after print bytes were sent is **uncertain**, and jobs active at restart become uncertain.

Consult [docs/protocol.md](docs/protocol.md) before changing these values. Record whether new information is APK-derived, observed on hardware, inferred, or proposed.

## Development and verification

Codex has a project-scoped `rust_lsp` MCP server (Serena backed by rust-analyzer).
Read its `initial_instructions` once when first using it in a session.
Use its symbol overview, symbol lookup, references and diagnostics when they help
with Rust navigation; use the usual Codex tools for edits. Read
[docs/codex-rust-lsp.md](docs/codex-rust-lsp.md) for setup and reconnect instructions.
The server is limited to navigation/diagnostics and does not replace Cargo checks.

Claude Code uses the native `rust-analyzer-lsp@claude-plugins-official` plugin,
enabled in `.claude/settings.json`. Use its `LSP` tool for Rust navigation when
helpful; see [docs/claude-rust-lsp.md](docs/claude-rust-lsp.md) for installation,
verification and restart instructions. Cargo checks remain required.

Run from the repository root:

```powershell
.\scripts\fetch-pdfium.ps1          # once; PDF tests and PDF preview need it
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
cargo run -p nuprint-cli -- test --preview output\test-preview.png
cd apps\desktop; npm ci; npm run typecheck; npm test
git diff --check
```

`cargo test -p nuprint-core` regenerates `apps/desktop/src/bindings`; commit regenerated bindings with the Rust type change. The desktop crate is not a default workspace member, so plain `cargo build` skips it; use `--workspace` or `-p nuprint-desktop`. The tauri crate family is pinned exactly in `apps/desktop/src-tauri/Cargo.toml` because older `tauri` releases broke against newer sibling crates; upgrade them together with `@tauri-apps/api`/`@tauri-apps/cli`.

For UI changes, run `npx tauri dev` in `apps/desktop` and inspect the changed screens at the default window size. `tauri dev` rebuilds and restarts the app when watched crates change, interrupting any job in progress. The frontend never builds packets, sees file paths or reaches raw GATT: native dialogs run in Rust, previews come from the `nupreview` protocol, and capabilities grant only app commands and event listening. Rust owns canonical rendering and printer I/O, and `btleplug` provides BLE only. Validate packaged Bluetooth and native rendering on each claimed OS/model; a library's platform support is not device-level evidence.

For protocol changes, regenerate fixtures only from the Python PoC (`poc/python/tools/gen_fixtures.py`) when the reference behavior itself changes. For packaging changes, run `npx tauri build` and launch the installed app; a dev run does not validate bundled PDFium or permissions.

No hardware is needed for the automated suite. CLI `scan` and `diagnose` and the app's **Check connection** do not print. CLI `test`, `text` and `file` print immediately unless `--preview` is provided. Respect existing user authorization for physical tests; if the current task is only documentation or offline development, do not consume paper. Do not repeatedly ask for permission already granted for the same action.

## Scope and collaboration

- V1 covers direct Bluetooth printing from the app and CLI, including NuPrint's own job queue. Windows system-printer/Print-dialog integration is deferred beyond V1. Its [future-work research](docs/future/windows-printing.md) is not an implementation requirement; revisit it only for a separately requested task.
- Keep changes scoped to the user's request. Do not silently install a printer queue, start a background service or alter Bluetooth/print settings.
- Keep the product name NuPrint and the `nuprint-*` crate names consistent. Do not add features to the Python PoC; keep it runnable as the parity reference.
- Read `git status` before edits. If another session changes the same files, reconcile ownership before replacing its work.
- Do not spawn subagents unless the user or another applicable instruction explicitly authorizes delegation.
- Commit source and documentation when asked; check staged paths and whitespace first. Pushing, publishing or releasing requires the corresponding instruction.
- Update current-behavior docs alongside behavior changes. Keep proposed architecture clearly marked as planned.

## Commits, pull requests and releases

- Never commit to `master`; a ruleset only lets it move through a rebased pull request with code-owner approval and passing CI. Branch as `<type>/<kebab-summary>`.
- Conventional Commits: `<type>(<scope>): <subject>`, imperative, lowercase, no trailing period, 72 characters at most. Types: `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `ci`, `chore`; scope is a crate or area, or `deps`. The body says why. One logical change per commit, never a co-author trailer, and no "Generated with" line in commits or pull request bodies.
- Pull requests are rebased, never squashed or merged, so each commit subject becomes a changelog line; `feat`, `fix`, `perf` and `refactor` are the visible ones. The body follows `.github/pull_request_template.md` with only true checklist items ticked.
- release-please (`release-please-config.json`, `.release-please-manifest.json`) owns versions, tags and `CHANGELOG.md`. Its release pull request bumps the workspace version in `Cargo.toml`, the workspace crates in `Cargo.lock`, `apps/desktop/package.json`, `package-lock.json` and `tauri.conf.json`, so never edit any of them by hand. Its pull request is opened by `github-actions[bot]`; the maintainer merges it through the admin bypass. Merging tags `vX.Y.Z` and opens a draft release; `.github/workflows/release.yml` builds the installers (NSIS, two DMGs, `.deb`), attaches them with `SHA256SUMS` and publishes the draft. A manual run of that workflow with a tag rebuilds an existing release.
- CI (`.github/workflows/ci.yml`) runs on pull requests only. It runs on its own only for the maintainer's (`wapenshaw`) pull requests; everyone else's waits at the fork-run prompt or at the `Approval` job's `ci-approval` environment. Never start a workflow (a manual run, a pushed tag or a pull request) unless the maintainer asks for it; check locally first.
- Release installers are not code-signed: macOS builds are signed ad hoc and Windows shows SmartScreen. Signing and notarization are tracked in [docs/backlog.md](docs/backlog.md).
